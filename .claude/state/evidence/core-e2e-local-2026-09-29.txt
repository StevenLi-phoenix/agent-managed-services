Observations (not fixed; recorded for follow-up)
------------------------------------------------
- A broken plugin gets two signals on two streams: core-sync's single `core_plugin_rejected`
  (above), and the harness's LogLine escalations of core's own `level:"warn"` lines
  (`plugin.failure`, `core.transition … outcome failed`). A failed core release also gets
  the harness's "giving up on core" next to core-sync's `core_release_failed`. Each stream
  dedupes itself, but the two do not know about each other. A platform-policy rule that
  suppresses core's own transition/failure lines in core mode would be a design decision
  (DECISIONS.md), so I did not make it here.
- Core probation can pass a plugin whose health always fails, when there is enough
  successful traffic (4a). That is api upstream behaviour, outside ams.
- Re-shipping reverted content deploys a new artifactId (buildInfo.commit changes), with a
  60 s probation, even when core already serves identical content (bacf6b… vs f27f1a…).
  Harmless, and it matches PLAN-core §4 ("a new commit with new content retries").
- core logs JSON lines on stderr, not stdout as PLAN-core §0 says. Harmless: the
  declaration's `[logging] format = "json"` classifies them on either stream.
